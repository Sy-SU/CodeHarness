# Experiments

`codeharness-experiment run/resume <experiment.yaml> --experiment-id <id> --confirm-model-call --confirm-submit` executes bounded sequential batches through `agent.execution.ExecutionService`. This service reuses CodingAgent, HarnessLoop, model/tool runtimes, OJClient and Workspace; it is not a second solver. `codeharness-report workspace` remains a read-only aggregate of existing State files.

Schema `phase5-v1` explicitly declares `name`, unique problem IDs (case-preserved, no surrounding whitespace), named strategies (`mode` plus fixed `profile` or mixed `roles`), `repetitions`, `model_config`, `harness`, HTTP/poll/deadline limits, expected/required Feedback Mode and a positive finite `total_cost_cny`. Model YAML paths resolve relative to the experiment YAML. At most 1000 tasks are planned; templates do not authorize or silently start runs.

`config/experiment.full.yaml` configures T1003 with four fixed standard/strong × mode groups plus explicit `mixed-harness` (PLAN strong, CODE/DEBUG standard), one repetition each, verdict_only required, default 1 CNY per task / 5 CNY aggregate allocation cap. Its historical filename is retained, but the requested condition and experiment name are now verdict-only. The template has the same five strategies. New experiment configs and shared execution requests also default to verdict_only/required. Historical `experiment.smoke.yaml` explicitly retains null/false, two standard modes and a 1-CNY aggregate cap, allowing unknown feedback only for smoke testing. Local/template output requests are now 8192 tokens; effective provider limits/tariffs are not independently verified. Escalation, model REVIEW and test generation remain disabled. No batch starts automatically.

Each task has an isolated workspace and frozen execution config. Reports under `workspace/.experiments/<id>/` include `manifest.json`, `tasks.json/csv` and `summary.json/csv`. Rows contain solved/verdict, terminal/reason, model attempts/successes/failures and per-Profile counts, tokens/missing usage, estimated cost/currency/status, cumulative reservations, POST attempts/confirmed submissions, DEBUG/replan/Custom Run counts, active wall time, solution hash/version/submission ID, actual/expected feedback metadata, condition fingerprints and Trace audits. Group summaries include unknown counts; null usage/cost is not zero. CSV escapes formula cells.

The grouping key includes strategy, actual configuration and observed feedback. Different effective budgets are different conditions; historical unknown-mode smoke is unverified. On 2026-10-02 `/api/v1/me` explicitly declared `feedback_mode: full`; contest 1 records actual full/effective verdict_only. Native verdict_only and a five-group live comparison remain unverified. Unknown/mismatched modes still block paid calls. Metadata changes require explicit adaptation, never inference from role/testcase details; historical snapshots remain unchanged.

New expected verdict_only tasks accept an explicitly declared full server mode via formal_verdict_only_v1. Remote formal results are projected to ID/status/verdict before traces, artifacts, checkpoints and prompts; even summary/error prose and unknown nested fields are withheld. Reports preserve actual_feedback_mode=full, effective_feedback_mode=verdict_only and feedback_policy. Such compatible conditions are verified only when metadata is confirmed and the effective policy is recorded; raw full, projected full, native verdict_only and unknown remain separately grouped. Missing metadata still stops, and native verdict_only cannot satisfy expected full. Policy fingerprints prevent old exact-verdict-only checkpoints/batches from silently changing behavior on resume; use new IDs. Public sample runs are unchanged.

Reservation guards apply to both modes. Each independent task (including repetitions of the same problem) has at most ten POST attempts and a configurable default 1-CNY budget, no shared per-problem cap. CLI `--max-cost-cny` overrides each task without raising YAML `total_cost_cny`. A smaller aggregate cap still reduces later allocations or exports `not_started`; those are not full comparable results. The formal 5-CNY cap permits five independent 1-CNY allocations, not automatic expenditure. Prices are user estimates, not invoices. Failed/uncertain calls retain reservations. Before a request, Runtime saves null cost/`pending_usage`; missing responses/usage remain null tokens/cost, never free. Provider bound violation stops the batch and blocks resume.

Intent is saved before remote work. Resume requires identical config, model routes/prices/parameters and endpoint fingerprints. Completed tasks are read without remote actions. Harness checkpoints restore existing responses/IDs; uncertain model calls/POSTs are never repeated. Interrupted code-only tasks become `result_unknown` and are not regenerated. No server-side idempotency guarantee is invented. A process restart never automatically resumes a batch.

Manifest fingerprints now freeze `budget_allocation: independent_tasks_v1`. Old shared-per-problem batch fingerprints cannot resume under new allocation semantics; existing reports remain readable. Changing output limits/price/budget similarly requires a new experiment ID. Resume cannot supply fresh funds to an old task.

Real smoke evidence: `phase5-live-T1003-20261001` completed two tasks, zero solved, four model calls, one failed public-sample run and zero formal submissions; both tasks ended `invalid_model_output`. Estimated configured cost 0.0421137 CNY, reservations 0.1490944 CNY; Feedback Mode unknown. ## Contest tests

`codeharness-experiment contest <contest-id> --experiment-id <new-run-id> --confirm-model-call --confirm-submit` reads visible public membership, freezes it, and executes one existing bounded task per problem. Use `--profile standard` for a fixed strategy; omitted harness profile uses configured Roles. `--max-total-cost-cny` defaults to 1 CNY for the whole contest, independent of per-problem `--max-cost-cny` (policy default 1 CNY). `--max-llm-calls`/`--max-submissions` limit each problem; code-only locks both counts to one. Contest-only flags are rejected for ordinary YAML experiments, not silently ignored.

`contest-resume <contest-id>` requires the identical model/policy/budget flags and run ID; the Dashboard restores saved settings automatically. `.contests/<run-id>/` holds the membership/config journal and lightweight JSON/CSV projection; `.experiments/<run-id>/` retains the full batch reports, with existing per-task checkpoints. Completed runs make no remote calls; unknown effects are never reissued. Blocked visibility/page schemas stop before paid calls; use a fresh ID after publication. Submissions go to the confirmed contest POST endpoint; there is no enrollment or server administration.

Scoring is deliberately `ac_count_only_v1`: solved+AC count / visible total and per-problem outcomes, with `official_score=null`. No weighted points, penalties or rankings. Only public HTTP pages are adapted because no contest-list GET JSON API exists; the adapter is bounded and fail-closed, without hidden data, editorial links or login.

Live `contest1-live-20261002` on contest 1: fixed standard/harness-loop, six calls/0.35 CNY per problem and 0.7 CNY overall; 1/2 AC, five model calls, two public runs, one formal submission (103, B accepted), cost estimate 0.0255813 CNY, reservations 0.241664 CNY. A's valid alternative permutation failed the existing token comparison; DEBUG returned no complete code, with no formal submission. That historical result is retained unchanged. New tasks use the frozen checker policy and positive-only unverified LLM checker gate; rejection does not request DEBUG.

## Current preparation and report evidence

`prepare config/experiment.small.yaml --experiment-id ID [--output NEW_FILE] [--freeze-model-config]` plans 12 × five × one = 60 tasks without invoking execution. Ratings/provenance, sample/feedback policy, conditions and allocation are frozen. Optional model snapshot loading has zero HTTP calls; prices/context/output verification remains null. Output refuses overwrite. The run command still requires the existing two explicit confirmation flags; preparation is not execution authorization.

Rows export actual model/roles, public rating, profile/policy, first_try_ac/recovered_to_ac/recovery_type, evidence links, sample reject/unverifiable counts, candidate/DEBUG/replan/formal/Custom Run counts and CNY estimates. Generated checker calls/remote runs/rejections are separately counted, while unverifiable decisions never earn sample recovery credit. Condition keys separate native verdict_only, projected full and unknown, budgets/model/samples policy and rating. Unknown costs/usage stay null. Summary never fills per-task Performance.

`contest-performance CONTEST_ID --experiment-id RUN_ID` independently reads me/standings and saves additive performance.json. Official integer performance is matched by the saved stable user_id, not rank/name; missing/invalid/unmatched/ambiguous data stays null with explicit status. The value belongs to the whole contest account and includes other runs; no isolated condition score or per-problem contribution is invented. Old runs lacking frozen account identity stay unresolved. The enrichment route neither loads model configuration nor runs Agent. Ordinary Dashboard GET/refresh polling only reads local files; the explicit protected performance refresh is separate.
